# Abandoned Cart Recovery and Conversion Attribution Pipeline
## Data Dictionary and Validation Specification

**Version:** 1.1
**Random seed:** 20261022
**Database:** MySQL 8.4
**Timezone:** UTC
**Default currency:** INR
**Tables:** 16 — 10 core entities and 6 supporting entities

## 1. Purpose and conventions

This document describes the database fields, identifiers, relationships, business rules, and validation requirements for the abandoned-cart recovery and conversion-attribution pipeline.

- **PK:** Primary key.
- **FK:** Foreign key.
- **UQ:** Unique constraint or unique index.
- Required means the database column is `NOT NULL`; optional means it accepts `NULL`.
- Timestamps are stored as UTC `DATETIME` values.
- Monetary values use the precision specified for each database column. The currency is recorded where applicable.
- Generated columns are calculated by MySQL and must not be inserted or updated directly.
- Event and consent histories are append-only records; historical events must not be silently overwritten.
- A database constraint and a business-rule validation are not interchangeable. Rules not enforced by MySQL must be checked by the generator or validation tests.

### Required identifier formats

| Entity | Format | Example |
|---|---|---|
| Customer | `CUS-` + six digits | `CUS-000001` |
| Session | `SES-2026-` + six digits | `SES-2026-000001` |
| Cart | `CART-2026-` + six digits | `CART-2026-000001` |
| Campaign | `CMP-2026-` + six digits | `CMP-2026-000001` |
| Message | `MSG-` + cart ID + `-01` | `MSG-CART-2026-000001-01` |
| Send attempt | `SEND-2026-` + six digits | `SEND-2026-000001` |
| Order | `ORD-2026-` + six digits | `ORD-2026-000001` |

Identifiers must be generated deterministically from the configured seed and sequence rules. Parent records must be created before dependent records. References must use the actual generated IDs, not independently generated approximations.

Event and line identifiers using `BIGINT AUTO_INCREMENT` are generated by MySQL and do not use the formatted business-ID conventions above.

# Part D — Global business rules

## 18. Abandonment and recovery

- Use a 24-hour inactivity threshold from the last qualifying cart activity.
- Determine abandonment from timestamps and cart lifecycle events, not independent random status assignment.
- A purchase that precedes an abandonment decision may invalidate abandonment under the business rules.
- Record lifecycle changes in `cart_events`.
- Calculate normal cart totals from active cart lines.
- Preserve removed lines and prior events for auditability.

## 19. Consent and campaign eligibility

- Determine consent separately for email and SMS at the exact send time.
- The latest consent event effective at that time governs eligibility.
- Missing contact information or invalid recipients must prevent the corresponding send.
- Suppressed assignments and send attempts must include a reason.
- The valid baseline must respect consent and frequency caps.
- Keep deliberate consent violations isolated as labeled anomaly cases.

## 20. Frequency caps

Configured policy:

- Maximum messages: 3.
- Window: rolling 7 days.
- Scope: customer and channel.

The generator must evaluate earlier relevant send attempts before allowing a new send. Test boundary timestamps and ensure a customer cannot evade the cap by switching campaigns.

## 21. Campaign variants

- Campaigns must have valid schedules and lifecycle states.
- Selected templates must match the campaign channel and be configured for that campaign.
- Where variant allocation is complete, allocation percentages must sum to 100%.
- Record the chosen variant and template so results can be compared later.

## 22. Attribution

Configured policy:

- Model: `LAST_CLICK`.
- Window: 168 hours.
- Duplicate conversion credit: prohibited in valid baseline data.

Attribution must be derived from documented campaign interaction and order timestamps. Do not randomly assign credited revenue or attribution labels independently of the underlying records.

The attribution model, candidate selection, tie-breaking rule, and treatment of cancelled or refunded orders must be documented in the generator and validation logic.

## 23. Ground truth and anomaly isolation

Ground truth must be stored separately from the ordinary input tables. It must identify affected record IDs, the anomaly label, expected validation result, and reason.

Required labels:

| Label | Meaning | Expected detection |
|---|---|---|
| `MESSAGE_SENT_AFTER_OPTOUT` | A message was sent after the applicable channel's opt-out took effect. | Consent validation failure. |
| `CART_ABANDONED_AFTER_PURCHASE` | A cart was incorrectly classified as abandoned after a purchase that invalidates abandonment. | Lifecycle validation failure. |
| `DUPLICATE_CONVERSION_ATTRIBUTION` | The same conversion received duplicate credit. | Duplicate-attribution validation failure. |
| `STALE_CART_TOTAL_AFTER_QUANTITY_UPDATE` | A quantity changed without updating the stored cart total. | Cart arithmetic reconciliation failure. |

Generate a valid baseline first. Inject deliberate anomalies afterward, label them in the separate ground-truth output, and preserve unrelated data integrity.

Ground-truth labels must not be used as input features by downstream detection or analysis logic.
